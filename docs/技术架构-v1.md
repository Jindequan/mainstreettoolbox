## 1. 系统分层

```
┌─────────────────────────────────────────────────────────┐
│  L1 工具面（静态, Cloudflare Pages）                      │
│  / · /{industry}/{tool} · /guides/* · /best/* · /services│
│  零门控 · 客户端计算 · localStorage+URL 序列化 · 无 cookie │
├─────────────────────────────────────────────────────────┤
│  L2 账户面（/app/*, Supabase + Stripe）                   │
│  magic link 登录 · 保存结果 · 收藏 · 客户档案 · 订阅管理   │
├─────────────────────────────────────────────────────────┤
│  L3 数据链（未来, 触发后才立项, 产品设计 §9.3）            │
│  Menu Costing Chain: 采购→成本分摊→菜单毛利→损益          │
│  = 预制模板链, 永不做自由 workflow builder                 │
└─────────────────────────────────────────────────────────┘
     concierge 定制服务横跨三层：人工交付，零新代码
```

**架构铁律**：L1 不依赖任何后端（断网也能算）；L2/L3 全部收在 `/app` 路由与独立子域化能力之后；任何后端故障不影响 SEO 资产。

## 3. 数据模型（Supabase PG）——**为 L3 预埋实体化接口**

核心决策：**保存结果从第一天起就是结构化的**（每工具的 inputs/outputs 有 zod schema，存 jsonb 并带 schema 版本），而不是不透明字符串。这样 L3 升级时 `saved_items` 可直接物化成实体表，无需用户重录。

```sql
-- L2 核心表
users            (id uuid pk, email unique, created_at, stripe_customer_id)
saved_items      (id, user_id fk, tool_slug, schema_version int,
                  inputs jsonb,      -- 工具 schema 校验过的输入
                  outputs jsonb,     -- 计算结果+诊断
                  label text,        -- 用户可改名: "芝士汉堡" "张三的家政报价"
                  created_at, updated_at)
favorites        (user_id fk, tool_slug, created_at)          -- 收藏工具
clients          (id, user_id fk, name, contact, notes)       -- Pro: 客户档案
client_documents (id, client_id fk, kind check(quote|invoice|report),
                  payload jsonb, saved_item_id nullable, created_at)
subscriptions    (user_id, stripe_subscription_id, status, price_id, current_period_end)

-- 上报事件(聚合, 无cookie, 可选参与)
usage_events     (ts, tool_slug, event check(pageview|first_input|result|save|email),
                  session_hash, user_id nullable)
```

**实体化升级路径（L3 触发时执行，非现在）**：
```
saved_items WHERE tool_slug IN (ingredient 类工具)  →  ingredients 表
saved_items WHERE tool_slug IN (menu-pricing 等)    →  dishes 表 (dish.ingredients[] → ingredients)
clients + client_documents                          →  不变, 直接复用
```
因为 inputs/outputs 有 schema，迁移是确定性映射而非猜测。

**RLS**：所有表 `user_id = auth.uid()` 行级隔离；client_documents 级联到 clients。

## 4. 工具工厂（36 个工具的批量生产方式）

每工具 = 一个声明式目录 + 一个引擎绑定，**页面/交互/SEO/埋点全部由模板产出**：

```ts
// src/tools/menu-pricing-calculator/config.ts
export default defineTool({
  slug: 'menu-pricing-calculator',
  industry: 'restaurant',                        // → /restaurant/menu-pricing-calculator
  engine: 'price',                               // 绑定 E2
  params: {                                      // 行业参数(引擎吃这个)
    benchmarks: { healthy: [28, 35], warn: 40 },
    defaults: { targetPct: 30, rounding: '95' },
    copy: { verdict: { /* ok/warn/bad 三态人话文案模板 */ } },
  },
  seo: { title: 'Menu Pricing Calculator', kw: ['menu pricing calculator', ...] },
  related: ['food-cost-percentage-calculator', ...],
  faq: [...], guide: '/guides/how-to-price-a-menu',
});
```

- `engine.ts`：把引擎适配为该工具的输入 schema + 计算调用 + 诊断生成（通常 <40 行）
- **新工具的平均成本 = 1 个 config + 1 个薄 adapter + 1 篇 guide**；全新行业 = 1 套 params/copy
- 引擎强制单测（vitest）：基准边界、诊断三态、除零/非法输入
- 这就是"参数化复用而非模板换词"的工程保证：每个工具必有真实引擎+行业基准+专属诊断文案

## 5. 关键流程设计

**认证**：Supabase magic link（邮箱→链接）；Google OAuth 次选；无密码。未登录用户一切可用。

**保存**：工具页 [Save] → 未登录存 localStorage（3 份上限，超额触发 Pro 提示）；登录存 `saved_items`。Copy link 与 Save 共用同一 schema 序列化。

**订阅**：Stripe Checkout（$9/mo, $79/yr）→ webhook 同步 `subscriptions`；Pro 功能门禁在服务端判（client_documents/保存数），客户端只做展示。付费墙位置见产品设计 §3.5。

**分析**：Plausible（cookieless，无横幅）+ 自有 `usage_events`（fetch beacons，聚合上报）。独立 GA/账号体系，**不复用矩阵任何 ID**。

**邮件**：Resend。两类：结果邮件（即时）+ Main Street Numbers 周报（nurture，含 concierge 位）。

## 6. 埋点漏斗与北极星

```
pageview → first_input → result_seen → save_click → email_captured → signup → subscribed
```
- L1 北极星：**周 email_captured**（基线 result→email ≥5%）
- L2 北极星：Pro MRR；服务线：月度 concierge 交付数
- 每工具一张健康卡：流量×转化×保存率 → 决定 Wave 内补哪类工具

## 8. 风险与对策

| 风险 | 对策 |
|---|---|
| 工具页被后端依赖拖慢/拖挂 | L1 纯静态红线 + CI 断言（工具页 JS<60KB、无运行时 API 调用） |
| 每工具schema漂移导致 L3 无法迁移 | schema_version 字段 + zod schema 强制 + 引擎单测 |
| Supabase/Stripe 单点 | 数据可导出（saved_items jsonb），迁移成本可控；Stripe 付费用独立 customer id |
| 36 工具量产时的质量稀释 | 上线五件套 checklist（工具清单 §6）+ 前端规范验收清单，缺一不发 |

## 10. v1.1 增补：SaaS Core 与 SDK 分层（架构裁决）

**三问三答**：①"不做后端"仅指 L1 工具页不依赖后端即可工作（SEO 护城河），不是产品永远无后端——M2 账户层就是后端。②SaaS Core（统一账号/计费/统计，全矩阵产品接入）是终局方向，采纳。③**Core 第一步"租"不"自建"**：一个共享 Supabase 项目（auth + Postgres 分产品 schema）+ 一个 Stripe 账户 = SaaS Core 首版；自建 Core 的触发条件 = ≥3 个产品接入 且 统一账号出现真实需求，未触发前自建 = 平台陷阱。

### 10.1 SDK 分层（代码已落地 src/sdk/）

```
L1 工具页（零后端铁律，断网可算）
   ↓ 唯一入口 getSDK()
SDK 四能力接口（src/sdk/types.ts）
   usage        — beacon / counts          【M1 已实现：worker 适配器】
   auth         — magic link               【M2：supabase 适配器】
   documents    — 菜单/计算结果/客户文档     【M2】
   entitlements — plan / limits（Pro 门禁）  【M3：Stripe】
   ↓ 适配器
local（现在） | supabase（M2） | core（将来自建，站点代码零改动）
```

- **站点代码只 import `getSDK()`**，永不直接 touch Supabase/Worker/fetch 后端。
- 适配器选择：`PUBLIC_SAASCORE_URL` 存在 → supabase；否则 local（usage 有 `PUBLIC_STATS_API` 则启用，否则静默）。
- 全部公开变量无密钥（.env.example）；Worker/D1 的 service 层在 Cloudflare 侧，密钥不进前端。

### 10.2 使用次数统计（M1 已实现）

- **端**：Cloudflare Worker + D1（worker/ 目录）——`POST /hit`（slug 白名单 + ip|ua 哈希去重，无法反推 IP）、`GET /counts?days=7`；反射式 CORS 只放行配置域名。免费额度 100k 写/天，零成本零运维。
- **语义**："使用" = 用户实际操作产生结果（计算器：改输入出结果；Workbench：导出/导入），每会话去重一次。
- **展示**：`[data-uses-for]` 元素有数据才显示（优雅降级——Worker 挂了/未部署，页面照常）；首页 essentials 列表 `data-stats-sort` 按真实使用量排序；无假数字承诺兑现。
- **迁移路径**：worker 能力即 SDK usage 适配器；SaaS Core 出现后并入其 `/usage` 端点，站点不改。
